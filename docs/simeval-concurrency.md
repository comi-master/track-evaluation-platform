# SimBench 并发与可靠性设计

SimBench 的并发压力来自评测任务，而不是来自上传页面本身：多个团队可能同时提交算法版本，单个算法版本可能触发大文件指标计算，Worker 还可能在计算期间重启。

## 并发场景

1. 多用户同时提交：`algorithm_submission.submission_key` 和唯一约束保证同一项目、Benchmark、协议、文件和算法版本只形成一条提交记录；应用层使用原子 `INSERT IGNORE`，不依赖异常回滚来处理竞争。
2. 同一提交同时点击评测：`evaluation_run.submission_id` 唯一约束保证只创建一个评测运行；应用层使用原子插入，竞争请求读取已经创建的运行并复用它。
3. 多 Worker 消费：RabbitMQ Listener 支持最小/最大并发消费者和 prefetch 配置。每个分析任务先通过数据库条件更新获得租约，只有持有租约的 Worker 才能写入结果。
4. Worker 故障：租约过期后，后续投递会恢复任务；达到最大尝试次数后进入失败/死信流程。
5. 结果查询与计算并发：评测结果查询会以数据库状态为准，质量门禁写入使用运行状态条件更新，避免重复生成门禁记录。

## 可调参数

`RABBITMQ_CONCURRENCY`、`RABBITMQ_MAX_CONCURRENCY` 和 `RABBITMQ_PREFETCH` 控制 Worker 并发度。默认值为 2、8、1，优先保证单个大文件任务不会被单个进程过度预取占满。

## 面试中的诚实表述

目前实现了数据库唯一约束、异步队列、Worker 租约、心跳、重试和死信路径；吞吐量、P95 延迟和可承载用户数必须通过基准脚本实测后再公布，不能只凭配置参数宣称高并发能力。
