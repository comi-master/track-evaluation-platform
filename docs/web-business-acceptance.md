# Web business acceptance continuation (2026-07-22)

Status: `IN_PROGRESS`.

The compatibility extension preserves REST/JWT and the three-source model. The same application provides database-paged dataset views, multipart CSV upload through the existing streamed MinIO/metadata service, parsed dataset detail, permission-checked original download, recoverable dataset deletion, asynchronous task creation/cancellation/retry/status polling, task-bound result display, and CSV result download. Administrators may widen dataset and task queries globally; non-administrators remain owner-scoped in SQL. V11 only extends the existing task state constraint with `CANCELLED`; V12 adds task leases, dataset deletion state, and the reliable outbox. V1-V11 were not edited.

Upload parsing failures run strict object cleanup before logical dataset cleanup. Web deletion refuses datasets containing multiple stored files so a partial multi-object deletion cannot damage an online dataset; such legacy datasets require a managed cleanup workflow. Critical web business audit writes are fail-closed. RabbitMQ redelivery of a RUNNING task is delayed through the retry queue and stale executions are recovered instead of being ACKed permanently. Results are loaded by the task's `analysis_result_id`, never by an unrelated latest file result.

`RedisIndexedSessionIT` uses an isolated `redis:8.2.7-alpine` Testcontainer for repository persistence, principal indexes, precise cross-user cleanup, TTL expiry, and explicit deletion. `AdministratorConcurrencyIT` runs two real MySQL transactions concurrently and proves that cross-disable cannot remove every administrator.

The in-app browser verified login, dashboard, dataset list, upload form, responsive overflow repair, real multipart upload, MinIO-backed parsing, and dataset detail. Its security layer then rejected the combined download/task-create interaction and prohibited browser-surface circumvention. Therefore task/result/admin/error pages are not claimed as visually accepted. The temporary browser account, indexed Session, credential file, and sample CSV were cleaned without deleting volumes.

The follow-up review reported three remaining High findings: time-based RUNNING recovery, cross-resource deletion, and audit failures after business commit. V12 work now uses a unique lease token, worker owner, heartbeat, expiry-only conditional recovery, token-guarded terminal updates, deletion states, and conditionally claimed Outbox work. Task publication is recorded before RabbitMQ publication, and dataset deletion request plus its critical audit and cleanup event share a MySQL transaction. Read/download audits are failure-tolerant so an audit outage cannot misreport a completed read as a failed business operation.

Current evidence after these changes: a clean Java 17 `verify -Pit` completed with `BUILD SUCCESS`; Surefire ran 109 tests and Failsafe ran 59 tests, all with zero failures, errors, or skips. Spotless and `git diff --check` pass. A real MySQL 8.4 run applied V1-V12 and validated all 12 Flyway migrations, including lease ownership and Outbox claim behavior. The rebuilt Compose image started with all five services healthy and upgraded the retained application schema from V11 to V12.

The isolated authentication smoke passed dual JWT/Session boundaries, CSRF, role isolation, user disable/enable, password reset/change, Redis principal-index cleanup, and audit assertions. The isolated end-to-end business smoke passed dataset creation, multipart CSV upload, MinIO-backed parsing and original download, transactional task publication, asynchronous `SUCCESS`, result page/CSV, administrator global task view, audit presence, recoverable object deletion to `DELETED`, processed deletion Outbox, and disabled-user JWT/Session invalidation.
